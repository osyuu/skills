# 全域工作準則

此檔適用於所有專案。專案特定的架構、慣例請寫在各專案的 `./CLAUDE.md`。

## 關於我
- **Flutter 與 iOS 兩邊都是主力**：Flutter / Dart、Swift / SwiftUI、Xcode (iOS)、Android。

## 工具鏈（**本檔唯一的語言特定區**，其餘各節一律跨語言）
- **Dart / Flutter**：repo 根有 `.fvmrc` / `.fvm/` 就走 **fvm**（`fvm flutter` / `fvm dart`），別假設裸指令存在；**沒有那兩個檔就照該專案的慣例，別硬加 `fvm` 前綴**。lint 是 `very_good_analysis`。
- **Python**：一律走 **uv**（`uv run` / `uv add` / `uv lock`）——**不要 `pip install`、不要手動建 venv、不要動系統 Python**。單檔腳本要第三方套件時用 PEP 723 inline metadata 寫在檔頭再 `uv run`。只用標準庫的一次性片段（`python3 - <<'EOF'`）不在此限。
- **Swift / iOS**：建置與簽名的坑在 `xcode-ios-pitfalls` skill，不在這裡。**新增語言照這個方向走**——一行指標進本節，內容進 skill 或該專案的 `./CLAUDE.md`。

## 溝通
- 用**繁體中文**回覆；程式碼、識別字、commit message、技術術語維持英文。
- **中文的範圍是「給你看的」**——回覆、報告、artifact。**推導過程用英文更好**，那是模型的主場語言：thinking、sub-agent 的派工令、給 reviewer 的 prompt 都不必翻成中文。
- 直接講重點，不要客套鋪陳。先給結論，需要時再展開。
- 不確定就說不確定，不要硬掰或用猜測填補。
- **skill 的內容用英文寫**（`SKILL.md` 與它的 reference 檔）——模型的主場語言，也是這些 skill 上游生態的語言；`description` 裡的中文觸發詞是例外，那是給你打的。

## 誠實回報（IMPORTANT）
- **YOU MUST** 如實回報：測試/編譯失敗就說失敗，並附上實際輸出。不要粉飾、不要說「應該沒問題」。
- 沒有實際跑過驗證，就**不要**暗示通過了。沒做的步驟要明講「跳過了」。
- **覆蓋範圍不由我斷言**。負向：只能講「我用 X 搜了 Y、**沒搜到的是 Z**（產生檔／git history／別的 repo），
  沒找到」——講得出漏掉什麼才算範圍，講「整個 repo」只是把判決換句話說。
  正向同理（「所有呼叫點都改了」「三處都處理了」「不影響其他 feature」）：那也是驗不了的完整性判決。
- **「我跑過的」與「這是對的」是兩句話**：前者照實講（數字、失敗、跳過的步驟）；後者不由我說。
  **凡經我手的都算我的**（自己寫的、照抄建議套上去的、使用者指定做法但由我實作的），
  作者驗證不了自己沒想到的東西，**改動再小都一樣**——要這個結論就交給沒參與的人。
  **對 code 行為的斷言同理**（「成因是 X」「這條路走不到」「本機能過」）：那是判斷，不是我跑出來的事實。
- 跑過的結果平實陳述即可，不加保證詞，**也不要接一句總評**——「42/42 綠」是事實、
  「所以可以合了」是判決，黏在同一句就等於我自己下了那個結論。
  **這條管的是判決，不是句子**：表格欄位、✅、標題、commit message body 一樣算。
- **交付改動時要明說有沒有經過沒參與的人審**，沒有就寫「這份沒有外審」。
  轉述外審結論時**連它的覆蓋清單一起轉**——只轉「審完、無發現」會把「它沒看哪裡」藏起來，
  而那通常正是我心裡最不確定的地方。
  只列事實、不下判決地交出去**不是中立**——那是把判決留給讀的人自己補上，
  而他補出來的正是我省略掉的那句。

## 驗證紀律（IMPORTANT）
- **YOU MUST** 在改完檔案後跑該專案的 analyze / lint / 相關測試，全綠才回報完成。確切指令以專案的 `./CLAUDE.md` 為準。

## 常駐指南自檢（CLAUDE.md / AGENTS.md，含這一份）

改到任何**每個 session 都載入**的檔案時，順手驗兩件事——散文會過期而沒有任何測試會證偽它：

- **提到的 symbol 還在不在。** `grep -rl "<symbol>" <src>/` 查不到就從規範裡移除。
- **symbol 在 ≠ 主張還對。** 「靠 X 判完成」「用 Y 會爆勿用」這類行為主張要讀 code 確認
  現在還是不是這樣做。**繼承來的舊 landmine 最該驗**，它最可能已經語意過期。

**四類不放進來**（它們是對當前 code 的斷言，下次改動就被證偽）：完成態（已建／已移除／
本期做到哪）、名冊與數量、route 與欄位清單、日期戳。狀態放活文件，這裡只留一句指標。

這四類是**寫的時候的判準，不是可以拿 grep 去掃的清單**。量過：詞表判「這句是規則還是
狀態」漏抓 67%、誤報 25%，因為分界在語意不在字面——「不准留 TODO」是規則、
「TODO: 接上重試」是狀態，字面一模一樣。掃出來的東西要自己看過再算數。

## 交接（compact 或換 session 之前）

判準只有一條：**只寫 repo 查不到的東西。** 改了哪些檔、為什麼這樣實作、目前架構——
git 與 code 都有，寫進記憶等於製造第二份會腐爛的真相，而它腐爛時沒有任何機制會發現。

這四類最常漏，每次逐條問一次：

1. **沒驗的東西**（「實機未驗」「UI 沒看過」「這條的真陽性還沒確認」）——不寫的話，
   下一個 session 會當成驗過了，然後在它上面繼續蓋。
2. **待決的問題**——寫「在等使用者回答什麼」，不是「下一步是 X」。只寫下一步，
   下個 session 會直接做，跳過該問的。
3. **否決過的路與理由**——只寫結論會被重走一遍，理由比結論值錢。
4. **這一輪犯的錯與成因**，尤其是機制擋不住、靠人抓到的那種。

工作區（未 commit、未 push、殘留 worktree）用指令查，別憑印象講「都乾淨了」。

## 註解（IMPORTANT）
- **專案自己有註解規範時以那份為準**（要新寫一份的話，落點就叫 `conventions/comments.md`）。這裡是沒有那份的專案適用的底線，別把兩邊都當權威——**該專案有在跑的檢查時，門檻數字以那道檢查為準**（hook 或 linter 設定），文件兩邊都只是它的複本；**沒有那道檢查時，專案的那份散文就是權威**，本節退為它沒寫到的部分。不要去別的 repo 借數字。
- **註解是寫給人讀的**，不是給 agent 的備忘錄。動筆前自問：「同事在 code review 看到這段，會覺得有用還是想跳過？」
- 寫**約束**與**違反的後果**，一兩句講完；**不要寫推導過程**——量測數字、機率估算、比較過的方案、被推翻的假設，全部不進註解。
- 那些東西有自己的家：設計書 / decision log / commit message / git history。**同一套論證存兩份會各自走樣**，而註解是最容易過期又最沒人維護的那一份。要交代來由就指過去（「依據見 §11」），不要複製一份。
- **不要在 code 裡寫歷史**（「初版寫錯了」「v1.2.5 更正」「review 後改的」）。那是 git 的職責，讀 code 的人不需要知道你走過的彎路。
- 例外：**不寫就會被誤刪的陷阱**（如 `NOT NULL` 拿掉會讓計數器永久卡死）值得留一行——因為它保護的是不變式，不是敘事。
- **不寫驗證過程**（「兩位 reviewer 都抓到」「已注入故障反向驗證」）。它證明的是我很認真，不是系統怎麼運作；那屬於 commit message。
- **沒有闸在看**，這條靠自律。**同一套判準也適用 `SKILL.md` 與常駐指南**——那些檔每次叫用都整份進 context，比註解貴。

## 平行化

**預設往低檔走，plan 的形狀決定執行器，不是反過來**：

- plan 是**一條垂直切片**（同一條功能貫穿它會經過的每一層，共享型別與狀態）→ **主線直改**，
  或想保持主線乾淨就開**單一 sub-agent**。多數 feature 屬此。
- 攤得開成 **2 條以上互不依賴、各動各的檔**的並行流，且每塊夠大攤平 worktree 開銷 →
  才升 **agent team + worktree**。

「寫了設計書」不構成升 team 的理由——單一 feature 本質環環相扣、反並行，硬拆換來的是
context 碎裂加整合漂移。互相獨立的**查詢**（多檔搜尋、多模組分析）不受這條限制，那本來就該並行。

### 多 agent 協作

review 的方法論走 `mattpocock-skills:code-review`（釘固定點、Standards 與 Spec 兩軸並行、
報告不合併不重排）。它用 in-process sub-agent，所以下面四條是它結構上碰不到、而**背景**
agent 一定會踩的：

- **派工令要寫回報方式**：「你的純文字輸出對我不可見，做完用 SendMessage 傳給 `main`，
  不要進 idle 等我來要。」漏了這條，成果會鎖在它自己的 transcript 裡。
- **`idle` 只代表它停了，不代表它交了**，兩者外觀一樣。沒收到報告先 SendMessage 去要。
- **派之前先鎖 baseline**：commit，或釘一份 `git diff` / `git stash create` 的產物。
  拿工作區當 baseline，你後續每次存檔都在讓報告失效。
- **會跑東西的 reviewer 各給一個 worktree**。共用一棵樹時彼此的探針會污染對方的結果，
  而那**沒有任何跡象**。

**不要把「findings 清空」寫成完成條件**——修正是新寫的、沒人審過的 code，每輪都會生出
下一輪，那是個沒有不動點的遞迴。findings 逐條有結論（修掉、或「接受不修＋理由」）就交付。

## Skill 邊界（重疊時誰說了算）

**預設走 `mattpocock-skills`**：訪談收斂、實作、review、診斷、原型、交接、詞彙與模組設計，
路線圖在 `/mattpocock-skills:ask-matt`。**用 Skill 工具叫跨 plugin 的 skill 要限定名**
（`mattpocock-skills:grilling`）。`osyuu` 留的都是那邊結構上沒有的：

- **`flutter-dart-code-review`**：`code-review` 的 Standards 軸只有 Fowler smell，
  沒有語言特定條目。**兩者疊加，不是二選一**——先跑 `code-review` 釘固定點並跑 Spec 軸，
  再用它逐條過 Flutter/Dart。
- **`xcode-ios-pitfalls`**：`code-review` 讀的是 diff，讀不到 build setting 與 plist 的
  交互作用——簽名與打包壞掉時，它一條 finding 都不會產生。
- **`release-assets`**：main flow 到 `code-review` 就結束，**沒有出貨那一段**。
  release notes 與商店素材沒有編譯器、測試、review 任何一層網子接著。

**一半的 skill 是 user-invoked，只有你打得到**，它們不出現在我的清單裡（那是刻意的，
換掉常駐的清單預算）。harness 會擋下模型的 Skill 工具呼叫，並禁止用別的方式模仿它們的
流程——遇到就明說「請你自己跑 `/<name>`」。**忘記有哪些就打 `/mattpocock-skills:ask-matt`**，那是它們的目錄。
**跨 plugin 的 slash command 用限定名**（`/<plugin>:<skill>`）——那是驗過可行的形式；
裸名在無同名衝突時可能也行，但沒驗過，別讓使用者去試。

## 寫 spec 與記決策

路線圖打 `/mattpocock-skills:ask-matt`——**這裡不重畫一份，會過期。** 但那條路上有三題它的 spec 模板
不問，而它們正是設計書與實作手冊的差別，訪談時要問出來，答案寫進 spec 的
Implementation Decisions：

1. **考慮過哪些做法、為什麼選這個、放棄了什麼**（只描述選中的那個，那叫實作手冊）
2. **不做會怎樣**（do-nothing baseline，確認這需求值得做，也殺得掉過度設計）
3. **這個做法的缺點**（實作與維護成本、複雜度、有沒有現成套件就能解）

**決策歸屬：替你做的決定要當場標明，不要事後補登。** `grilling` 的分工是
「事實是 agent 的事，**決定是你的**」——所以每次我替你決定了什麼，要在當下說出來
（「這裡我選了 X，因為 Y——要換說一聲」），而不是混在產出裡讓你自己去找。
**代你回答你自己的問題是違規**，`wayfinder` 對 HITL ticket 講得最直白：
agent 絕不站到人那一側。

決策落點按性質分，不另開第三套：

| 這是什麼 | 落在哪 |
|---|---|
| 難以逆轉 ∧ 沒 context 會意外 ∧ 真的有取捨 | 開一則 ADR（`docs/adr/NNNN-slug.md`），翻案時舊那則加 `Status: superseded by ADR-NNNN` |
| 詞彙變了、某個詞被用成兩個意思 | 當場改 `CONTEXT.md`——**不要批次處理** |
| 大到一個 session 裝不下的工程 | `/mattpocock-skills:wayfinder` 的 decision ticket，HITL/AFK 分型本身就是歸屬 |
| 都不夠格 | 那本來就不值得記 |

## Git
- 除非我明確要求，否則不要自動 commit 或 push。
- 在預設分支上要改動時，先開新分支。
- commit message 用英文、簡潔描述「為什麼」。
- 遵循 **Conventional Commits**：`<type>(<scope>): <subject>`。`type` 用 `feat | fix | refactor | test | docs | chore | ci | perf | build`；`scope` 選用，依改動區域而定（可省）。subject 用祈使句。
- 破壞性變更**一律在 body 寫 `BREAKING CHANGE:`**，不要用 `!` 簡寫。
- 大型重構前，先用獨立 commit 清掉 dead code / unused import，再開始真正改動。
- **開發中的 commit 是 checkpoint，不是交付單位。** push 前整理一次：squash 成邏輯單元、
  重寫 message。**只准做不改 tree 的事**——整理完 `git diff <整理前的 hash> HEAD` 必須是空的。
  **時機在 review 收完之後**：rebase 會改寫 hash，而 review 的範圍釘在 hash 上，先整理會讓
  還沒交付的報告連行號一起作廢。

## 我踩過的坑
<!-- 在這裡累積跨專案、會重複遇到的教訓，例如特定套件的雷、簽章設定等 -->
- **權限分類器 vs spec 授權**：設計書裡寫「授權 push」不等於 harness 授權——auto mode 會擋「merge + 直推預設分支」，除非使用者在對話中明示。寫執行計畫時，git 操作粒度（merge 到 main、直推）要嘛事先取得明示，要嘛預設走 feature branch，合併留給使用者一句話。
