# Requirement → Detailed Design Document

把需求變成一份**輕量契約 + 驗收清單**，給後續的 plan 與 code 當依據，並在實作後當驗收標準回頭檢查。

## 核心理念（先讀，這決定品質）

設計書對 AI 生成 code 的真正價值，**不是文件好看，而是在寫 code 前把模糊點逼到收斂**。AI 生成最大的不穩定來源是需求欠規格（underspecified）：需求一模糊，模型就自己腦補、中途漂移。設計書的工作就是把這些腦補點變成白紙黑字的決定。

判斷一行內容該不該寫，只有一個判準：**「如果不寫下來，AI（或別的工程師）會不會猜，而且可能猜錯？」**——以下把這種地方叫**猜測點**。會猜 → 寫。不會（顯而易見或純風格） → 省略。這份 skill 的每個步驟、每個掃描項，都是在找猜測點。

所以這份文件的定位是**介面與行為層的契約**，不是實作說明書。要避開三個傳統「詳細設計書」的陷阱：

1. **不要寫虛擬碼 / 逐函式實作**——那等於把 code 抄一遍，馬上過時、又綁死實作，AI 反而被綁住。實作交給 code。
2. **粒度停在介面與行為**——寫到「這個介面收什麼、吐什麼、錯誤怎麼處理、狀態怎麼轉」就停，不往行級寫。
3. **詳細要詳在猜測點密度最高的地方**——資料模型、介面契約、**狀態轉換、邊界條件、錯誤處理、驗收標準、非目標**。這些是 AI 最常猜錯、且不會隨實作細節變動而立刻過時的部分。

### 五個讓設計書真正有用的原則（業界共識 + SDD）

前四條來自 Google design doc、ADR、Rust/PEP/KEP/React RFC 等公開實務；第五條來自 spec-driven development（spec 驅動 AI 實作）的教訓：

1. **設計書的存在理由是「取捨與被否決的替代方案」**。只描述你選的那個解法，那叫實作手冊，不是設計書。一定要寫「考慮過哪些做法、為什麼選這個、放棄了什麼」——這是文件最有價值的部分，不能省。
2. **逼問「為什麼不要做這個」(drawbacks) 與「不做會怎樣」(do-nothing baseline)**。強迫自我批判：實作/維護成本、複雜度、有沒有現成套件就能解。這能殺掉過度設計。
3. **先寫問題、獨立於解法 (constraint-first)**。背景與目標要能「即使你的設計被推翻，仍然成立」。把約束條件寫清楚，不要綁死在你選的解法上——這樣文件壽命更長。
4. **右尺寸，必要時不寫**。不是每個需求都要整份設計書。解法顯而易見、低風險 → 別寫，直接做或寫幾行 plan 即可。風險高、不確定、跨團隊、工程量大 → 才值得完整寫。長度隨風險縮放：小需求 1~2 個重點章節就好，別硬湊滿模板。**先判斷「這需求值不值得寫設計書」，再決定寫多細。**
5. **（SDD）spec 是給實作者的工單，也要持續是單一真相**。實作 AI 拿這份文件工作時，不該有任何需要「發明語意」的地方；文件要列全**交付物**與**可執行的驗收方式**；實作偏離或決策翻轉時，**同一批改動就回寫文件**（版本 +1），不讓 spec 與 code 漂移。⚠️ 護欄：SDD 補強止於此——**不要**引入 requirement ID、追溯矩陣、EARS 句型等重形式；右尺寸原則（第 4 條）優先於完整性。

## 工作流程

### Step 0 — 取得需求

確認需求來源並讀進來：
- **禪道 (ZenTao) story / bug / task**：若使用者給了 story ID，用對應的 zentao skill 取得內容（如 `zentao-story`）。
- **貼上的文字 / issue / 既有規格檔**：直接讀。
- 來源不明確就先問：「需求在哪？story ID、檔案路徑、還是直接貼給我？」

### Step 1 — 抽取 + 反問（收斂發生在這裡）

讀完需求後，**第一個產出是問題清單，不是設計書**。列出需求中的模糊點、隱含假設、缺漏，整理成幾個有重點的問題回問使用者。這一步是整個 skill 的價值核心。

問題要**聚焦在猜測點**——不問清楚就會猜錯的地方。顯而易見或可合理預設的不要當開放題問（那種直接帶預設值、在文件裡標註即可）。用 `references/clarify-checklist.md` 挑真正有缺口的面向，一次問完（通常 3~6 題就夠）。

提問時：
- 對能合理推定的部分，**直接給預設答案讓使用者確認/否決**（降低使用者負擔），例如「我假設未登入者不能存取，對嗎？」
- 真正開放、影響設計走向的，才當開放題問。

**收斂判準**：`references/clarify-checklist.md` 的每個面向都已經「有答案」或「明確標為不適用」——**判準是面向覆蓋，不是題數**。使用者回答後若又冒出新的模糊點，可以再問一輪；剩餘的未知放進文件的「待確認事項」。

**拿不到答案時的 fallback（非互動場景）**：若是排程、批次、headless 等無法即時得到使用者回答的情境，不要卡住。改成：把原本要問的問題**連同你採用的預設答案**寫進文件開頭的「釐清問題與假設」表，關鍵的猜測點就地標 `【假設】`，然後依這些 stated assumptions 把設計書寫完；真正影響設計走向、需要拍板的，再列進「待確認事項」。原則是**讓所有替使用者做的決定都可見且可被推翻**，而不是停下來等。

### Step 2 — 生成設計書

用 `assets/design-doc-template.md` 當骨架產生內容。**各章節怎麼寫、章節怎麼裁剪，模板自己講**；這裡只講模板沒說的：

- **先右尺寸再開模板**（原則 4）——不是開了模板才想要不要縮。
- **替代方案與 constraint-first 砍不到**（原則 1、2、3）：右尺寸縮的是篇幅，不是這兩節——少了它們，這份就只是實作手冊。
- **每個被你做的假設與決策都要可見**：寫進「設計決策」或就地標註，讓使用者一眼看到你替他決定了什麼。
- **語言**：跟著對話語言（預設繁體中文）；程式碼、識別字、型別、API 名稱、欄位名維持英文。

**SDD 完整性掃描（初稿完成後、寫檔前必跑）**：讀 `references/sdd-scan.md`，十項逐項自問，每項標「已處理」或「不適用＋一句理由」——**不留空白，空白會被讀成掃過了**。

### Step 3 — 寫檔 + 版控歸屬

1. 產出路徑：`docs/design/<slug>.md`（`<slug>` 用 kebab-case 的需求簡稱，例如 `user-login-otp`）。`docs/design/` 不存在就建立。
2. **不要自作主張改 repo 的 git 設定**。寫完檔就停手：它是個 untracked 檔，會出現在 `git status`，使用者在 commit 當下自然看得到。這是零設定、兩個方向都還能輕鬆回頭的狀態——自動排除或自動 commit 都是替使用者做了他沒同意的決定。

3. **版控歸屬：每個 repo 問一次，之後靠偵測**。先找既有訊號，有訊號就照做、不要再問：
   - `git ls-files docs/design/` 有輸出 → 這個 repo 的設計書**進版控**。
   - `git check-ignore -v docs/design/<slug>.md` 命中 → **不進版控**。
   - 兩者皆無 = 這個 repo 第一次寫設計書 → **問使用者一次**（有結構化提問工具就用它），兩個選項：
     - **進版控**（repo 已有 CI、SDD harness、或多人協作時建議）：設計書是團隊共享契約，進得了 PR diff / CI / fresh agent 的視野，回寫才有強制力（見 Step 5）。
     - **不進版控**（個人設計筆記）：追加一行 `docs/design/` 到 `.git/info/exclude`——用本機個人排除，不去污染團隊共用的 `.gitignore`。

   **把答案變成下次的訊號**，否則每次都要重問：選「不進版控」時寫進 exclude 這動作本身就是訊號；選「進版控」則提醒使用者把檔案 commit（commit 前 `git ls-files` 仍是空的）。repo 若有 CLAUDE 檔且已有設計/SDD 相關章節，順手補一行寫明歸屬，讓下一個 session 與其他 agent 不必重新推斷。

   **拿不到回答時**（排程、批次、headless）：不要猜、也不要動 git——檔案留 untracked，在回報裡明講「版控歸屬未定，請在第一次 commit 時決定」。這比猜錯任一方向都便宜。

4. 寫完後回報：檔案路徑、關鍵決策、待確認事項，**並明講目前的版控歸屬**。若是不進版控，補一句風險：會被 commit 的檔（如 `CLAUDE.md`、`DECISIONS.md`）若指向這份設計書，對隊友 / CI 就是懸空指標。**把它 flag 給使用者，別自己改指向或強制 commit**——那是專案相依的決定，不歸這裡管。

### Step 4 — 銜接 plan（選用）

設計書定稿後，它就是很好的 plan 輸入。若使用者要接著實作，建議進 plan：用設計書的「整體設計 / 資料模型 / 介面契約」推導實作步驟與檔案改動順序。設計書回答 WHAT/結構，plan 回答 HOW/順序，兩者互補。

### Step 5 — 回環驗證 + 回寫（spec 當工單用時**非選用**）

實作完成後，回頭拿設計書的「驗收標準」逐條檢查實作是否符合。這把設計書變成可驗證的閉環，是「增加開發穩定性」的關鍵——不要只生成、不回收。**spec 一旦被當成工單，這步就不是加分項**：寫得出一整頁驗收標準卻一條都沒跑，那份標準只是文件的裝飾。跑不了的條目要**明寫「跑不了、為什麼」**，不要留空——空白會被讀成通過。

**由誰跑：不是作者。** 派沒參與實作的 agent；視角按這次改動的性質選，一個視角要成立的條件是**它能抓到別的視角結構上抓不到的缺陷類別**，一個視角一份獨立報告。

**為什麼不能自己審**：知道自己為什麼那樣寫，正好使人看不見那個假設是錯的——回頭讀那段 code，讀到的是當初的意圖，不是它實際做的事。**綠燈的 analyze 與測試證明不了這件事**：它們只看得到你寫下的東西，看不到你沒想到的東西。

**回寫（SDD：spec 保持單一真相）**：實作過程若偏離設計（欄位改名、行為調整、決策翻轉），**在同一批改動裡更新設計書**——版本 +1、文件資訊表加一行變更記錄（一句話講改了什麼＋為什麼）。過期的 spec 比沒有 spec 更危險：它會主動誤導下一個讀它的人（或 AI）。

**回寫的強制力（別只靠事後記性）**：回寫最常見的失敗是「交付前憑記憶重建所有翻案」——那一刻 context 最稀、又常剛被 compact，最不可靠。把回寫拆成四環看：①**察覺**翻案、②**記錄**、③**觸發**回寫、④**驗證** spec 真的改了。①是純語意判斷、無法機械化（沒有工具能從 diff 看出「這是一次決策翻案」）；能被確定性保證的只有「**已記錄**的決策一定被回寫+驗證」（③④）。所以：

- **把「記錄」壓到決策翻案的當下**，不留到末尾——當下 context 最全、動作最小（就地在文件標 `【決策變更】` 或附一行到變更記錄草稿），且**寫進檔案即穿過 compact**。這是唯一能拉高①②可靠度的槓桿。
- **把回寫列進任務 DoD**：「本任務若翻案/新增決策 → 同批交付 spec delta」與 code/test 同級，漏寫＝未完成。責任落在執行 agent 當下，不落到 leader / 下一個 session 的記性。
- **確定性 gate 需要 spec 進版控**：merge / PreCompact hook 只有在 spec 進得了 PR diff / CI / fresh-agent 視野時，才擋得住漂移；**git-excluded 的 spec 沒有任何機制強制回寫**，只能靠上面兩條把殘差縮小、消不掉。要「可強制」就得把該 spec commit 進版控。

## 品質檢查（寫檔前自問）

- 這需求**值得**寫這麼長嗎？有沒有為了填滿模板而灌水？（右尺寸優先於完整性；requirement ID / 追溯矩陣 / 為掃描而灌水 → 刪）
- 逐條回頭核對五原則：替代方案與「不做會怎樣」寫了嗎？背景 constraint-first 嗎？我替使用者做的決定都可見嗎？
- `references/sdd-scan.md` 十項都標了「已處理」或「不適用＋理由」嗎？三件交付要求呢？
- 驗收標準每一條都可驗證、且各自標了驗證方式嗎，還是混了形容詞？
- 有沒有寫成虛擬碼 / 抄 code？不適用的章節是刪掉或標 `N/A`，而不是留空殼？
- 範圍 / 非目標寫清楚了嗎？AI 照這份做會不會做超過或做不夠？
- 若填了任務分解：每條都指回規格章節而非複述？依賴是真依賴？單人單 session 的需求是否誤填了本節？
- 若設計書含自動化執行計畫（agent 團隊執行）：授權邊界有沒有明列 git 操作粒度（開分支、merge 到預設分支、push、部署）？注意 spec 裡的授權**不等於** harness 權限層的授權——「直推/合併預設分支」需要使用者在對話中明示，寫計畫時預設走 feature branch、合併留給使用者拍板。
