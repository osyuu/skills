# SDD 完整性掃描

Step 2 初稿完成後、寫檔前逐項自問。這十項是「實作 AI 一定會踩到、需求方卻幾乎不會主動講」的高頻**猜測點**——有涉及就補進文件，不涉及就跳過（別為掃描而灌水）。

各章節**怎麼寫**由 `assets/design-doc-template.md` 說了算，這份只管「有沒有漏」與「踩過什麼」。

## 1. 資料生命週期

每個新 entity 的「父資料被刪/改時怎麼辦」寫了嗎？cascade 清理、孤兒列策略、反正規化 counter / 冗餘欄位的回減，缺一個就是資料 bug。→ 模板 §6。既有的刪除路徑要**實際去讀 code 確認現況**，不要假設。

## 2. 自動產生資料的欄位預設

任何由系統自動建立的 row（backfill、upsert 附帶建立），每個欄位填什麼要白紙黑字（NULL？預設值？誰之後補？）。

## 3. 限制與 clamp

分頁上下限、字串長度、數值範圍、格式驗證——沿用專案既有慣例並寫明數字。

## 4. 跨介面語意一致性

相似操作（如兩種寫入端點）的驗證/錯誤語意一致嗎？**刻意不同**的地方要寫明「與 X 刻意不同，因為…」，否則實作者會自行類推統一。→ 模板 §7。

## 5. 顯式接受風險

刻意不緩解的風險（濫用、無認證寫入、資料膨脹…）有逐條落到模板 §11 的「顯式接受的風險」嗎？沒寫下來的接受，review 時會被重新翻案。

## 6. 自我延續機制的收斂性

任何會反覆觸發自己的機制（分頁／無限捲動、retry、輪詢、debounce、auto-advance、心跳）要寫明三件事：

- **每次迭代由什麼驅動**（滑到近尾端？事件？計時器？）
- **終止條件與其權威來源**——`hasMore`／停止旗標要來自單一真相（後端 `total`、明確 flag）。「回滿一頁就假設還有」需要兩個數字手動同步，不算單一真相。
- **驅動參數取退化值時仍成立嗎**——page size=1／空頁／清單短到無法再滑，觸發還會 fire、終止還會收斂嗎？

踩過：loadMore 只綁滑動觸發，page_size=1 時無下一頁可滑 → 永不觸發 → 卡死。

## 7. 共享可變狀態的併發模型

先問一句「**這個狀態有幾個 writer**」——只有一個就跳過整項。**兩個以上**就把模板 §8.1 整節填滿（writer 清單／交錯裁決表／副作用落點／選定的形狀）。

模板沒說的那條：**旗標的涵蓋範圍要蓋滿自己所有的 `await`**——只在進場檢查、不整段持有等於沒有旗標，它擋不住的正是它存在的理由。

踩過：設計書只寫了「背景任務 vs 使用者動作」一種交錯，於是「使用者 vs 使用者」與「動作 vs 尚未完成的 build」兩個象限全裸，各出一個 P1，都在**上一輪修正過**的程式碼裡。另一次是某個 in-flight 旗標只由一條路徑持有，另一條同樣會改寫狀態的路徑僅檢查它——它兩段 `await` 期間門戶洞開，其中一段還是可能觸發網路 I/O 的。

## 8. 對框架／OS／外部服務行為的宣稱，一律附出處或標為未查證

寫「這個 API 在 X 情況會失敗」「這個機制會自動 Y」之前，要嘛讀過並標出處（檔名行號、SDK header、官方文件），要嘛照第 5 項的格式明寫「未驗證」。→ 模板 §8.1 的「依賴的框架行為」表。**沒查證的宣稱看起來跟查證過的一模一樣**，那正是它危險的地方。**宣稱會流進使用者可見字串時，這條升級為硬性要求**——設計書裡一句沒驗證的邊界條件，會原封不動長成八種語言的錯誤文案，而到那時已經沒有人會回頭質疑它。

踩過：把沒讀過的框架去重語意當不變式寫進 CLAUDE.md——它其實只對值路徑去重，錯誤路徑無條件通知。另一次是設計書寫「檔案被移動或刪除時 bookmark 會失效」，但 iOS 的 security-scoped bookmark 靠**檔案 ID** 追蹤、移動照樣解析得到——而該專案自己的 code 註解就寫著這件事。那句話已翻成八語言送到使用者面前，靠實機驗收才抓回來。

## 9. 規格裡的判定詞要有可判定的定義

每個「成功／完成／有效／已送出／存在」都要能回答「**失敗長什麼樣**」。當底層的失敗回傳長得像成功（非 null、空清單、預設值、部分成功），實作一定會挑最方便的那個判準，而那個判準通常是錯的。

踩過：規格只寫「送完逐則加進列表」、沒定義什麼叫送出成功，實作用了 `isNotEmpty`；而該 SDK 送失敗仍回一則非 null 的訊息，於是送失敗被當成送出去了——那筆狀態在本機永久鎖死，對方卻什麼都沒收到。

## 10. 多步序列逐步問「這一則缺了會怎樣」

第 9 項定義「失敗長什麼樣」，這一項問**每一步失敗的後果**——N 步流程有 N 種部分失敗，而**答案常常不一樣**。形狀相同不代表嚴重度相同，答案不同的要分別寫明，否則實作者會套同一個判準。

踩過：三則訊息的流程，中間那則缺了只是少一句提示，最後那則缺了整局狀態就壞掉；差點被統一成「全部成功才算成功」，而那會讓使用者以為沒送出去再送一次，對方收到兩份、變成兩局。

## 三件 SDD 交付要求

掃完十項，再確認：

- **交付物清單**列全了嗎（code、migration、**版本化契約文件**、驗證腳本、輔助工具）——漏列的交付物 = 不會被做。
- **每條驗收標準都標了驗證方式**嗎（自動測試 / 腳本 / 手動步驟）？若環境跑不了本地測試，驗證腳本本身要升級為交付物。
- **每條不變式標了「什麼在守它」**嗎（測試／hook／型別系統／**無**）——「無」是可接受的答案，但**必須寫出來**，否則沒人會發現它裸著，而裸著的不變式下一次改動就會被還原。
