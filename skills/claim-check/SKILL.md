# claim-check — 讓「我說我做了」與「我實際做了」對得起來

## 這道 hook 在解什麼

寫 code 的那一側已經很擁擠：編譯器、測試、型別、lint、pre-commit。**但 agent 講給人聽的話沒有任何東西在看。**

於是同一個 agent 可以：

- 說「audit 還在跑」，而那一回合只發出過一次 grep
- 說「測試綠」，而最後一次跑測試之後又改了三個檔
- 被質疑時生一段技術理由來守住已經講出口的結論，而那段理由**與它自己稍早讀過的檔案相反**

這三種都不會讓任何測試變紅。唯一的偵測者是使用者，而那是最貴的一種——**他得先相信你、再花時間去查，才發現查的是你編的東西**。

`Stop` 事件同時給得到「剛講的那段話」與「這一回合的工具呼叫」，是把這件事關起來的位置。

## 流程

**1. 裝**（idempotent）：

```
sh <skill-dir>/scripts/install.sh
```

寫 `~/.claude/hooks/claim-check.py`，把 `Stop` hook **附加**進 `~/.claude/settings.json`（不覆蓋既有的 Stop hook，覆蓋等於靜默停用別人的）。

**2. 先 warn，拿真實對話回放定基準**——這步不要跳過：

```
python3 ~/.claude/hooks/claim-check.py --replay ~/.claude/projects/<proj>/<session>.jsonl
```

**對七成回合開火＝噪音，會被學會忽略；完全不開火＝等於沒裝。** 一個 424 回合的真實 session 校準到 15%，其中兩條規則（測試／build）貢獻了三分之二的開火而真陽性未經確認——那正是 warn 期要判的東西。

**3. 每條規則都拿得出真陽性，才切成擋**：`export CLAIM_CHECK_BLOCK=1`。判準不是「感覺誤判變少了」，是逐條過——舉不出真陽性的規則，warn 期結束就砍掉、不要帶進擋的模式（見〈規則怎麼設計〉末段）。**擋在高誤判率下，人會直接關掉整個 hook**，那比沒裝還糟。擋下來的成本是 agent 多跑一次，不是使用者的時間。

## 規則怎麼設計（這比腳本值錢）

**每條規則都要能只用工具呼叫紀錄判定。** 判不了的（「這個設計比較好」）不要寫進去——加一條抓不準的規則，代價是整個機制被學會忽略。

三個踩過的坑，直接寫進預設規則裡：

- **不要判「這一回合有沒有跑」。** 引用前幾回合真的跑出來的結果是正常的，那樣寫會把大量真話標成假話（實測 23% 開火）。真正的不變式是**新鮮度**：跑完之後有沒有再改過 code。這順帶蓋住「還原注入的故障後沒重建就跑測試」那個坑。
- **背景宣稱要有時效窗。** 背景工作跨回合活著，所以不能只看本回合；但也不能看整個 session——十個回合前啟動、早就收工的 agent 不能當「現在正在跑」的證據。
- **「被質疑後有沒有讀東西」太弱，要問「有沒有讀你正在下結論的那個東西」。** 實測那次，該回合讀了兩個檔，但結論的對象是第三個檔，從頭到尾沒打開過。

**逐段判，不要整段判。** 同一回合常常是「跑測試 → 報告結果 → 接著改下一處」，整段判會把後面那次 Edit 當成「宣稱之後又改過」。文字與工具呼叫在紀錄裡是交錯有序的，拿宣稱自己的位置去比才對。

## 已知擋不住的

- **把自己的發明說成對方的意思**（「我猜你指的是這件事」）——要判斷語意，不做。
- **引用了真實證據但推論錯誤**——這是判斷力問題，不是誠實問題，本 hook 不處理。
- **發明不存在的 API**——編譯器／型別檢查已經在守，不要重複。

規則清單刻意短。**每加一條就要先回答「它的真陽性長什麼樣」**，答不出來就別加。

## 品質自檢

- 裝完有沒有拿真實對話回放過？開火率落在哪？
- 每條規則都舉得出**這個 session 裡**的一個真陽性嗎？（這是切成擋的前提，見流程 3）
- 規則是對著「自己的假話」調的，還是照抄別人的樣本？後者不會準。
