# 多 agent 協作房規

背景 agent 最貴的不是 token,是**你以為它做了、其實沒有**。這份的重點都在那些「看起來成功了的失敗」:報告沒送到卻顯示 idle、agent 照舊規格做完才發現規格改了、兩個 writer 撞同一個 worktree。

---

## 一、開之前

- **先盤點現有的**(列不出來就問使用者)。名稱衝突會長 `-2`(identity 分裂)。有對口就 `SendMessage` 復用,別重開。

  | 想做的事 | 用這個 | 別靠這個 |
  |---|---|---|
  | 列出現有 agent | `TaskStop` 丟一個不存在的 id,錯誤訊息會附 `Running teammates: ...`;再不行問使用者看 `/tasks` | `ListAgents` 回空**不代表沒有**;`TaskList` 列的是任務不是 agent |
  | 確認某個名字還在不在 | `SendMessage` 指名送一則,送得到就活著 | — |
  | 停掉 | `TaskStop`,吃名字,跨 session 也吃 | `TaskOutput` 只吃 task ID,不吃名字 |

  **上個 session 留下的 teammate 對新 session 是隱形的**——不在 `ListAgents`、不在你的 spawn 記錄裡,上面那招也只確認得到本 session 的。所以盤點的最後一步還是得問使用者;不問就會在它們還掛著的時候又開一輪。

- **按任務性質分 model**:async/併發/生命週期/測試 harness → 強模型;規格鎖死的機械 UI → 輕模型。
- **大改跨檔用 worktree 隔離**,主 tree 保持穩定給別的並行工作(QA/截圖)。

## 二、派工令必備六條(漏一條都有實證代價)

1. **唯讀還是可寫**,講死。review/調研一律唯讀:「不要編輯、新增、刪除任何檔案,也不要 commit」。
2. **回報方式**:
   > 你的純文字輸出**對我不可見**,必須用 **SendMessage 工具**傳給 `main`(或 `team-lead`)。做完就傳,**不要進 idle 等我來要**。

   不寫這條,agent 會安靜跑完然後 idle,成果鎖在它自己的 transcript 裡。這是最常見也最貴的失敗。
3. **範圍**:commit 區間(`git log --oneline <base>..HEAD` 貼上)+ 背景文件路徑 +「完整讀完」。
4. **必查清單**:具體到「這個函式在這四種情境下各會怎樣」,不要只給主題。
5. **排除既有雜訊**:「`test/xxx` 的 N 個失敗是既有的、與本次無關,不要當成你的發現」。不寫的話報告會被既有紅燈灌水。
6. **回報格式與誠實要求**:
   > 格式:「檔案:行號 / 嚴重度(P0阻斷|P1應修|P2建議) / 具體失效情境(什麼操作序列 → 什麼錯誤結果)/ 建議修法」。
   > 不要提無實質影響的風格意見,也不要為了湊數硬報。不確定就明說不確定,並講清楚**需要什麼證據**才能確認。沒問題就說「審完、無發現」,並列出你**實際驗證了哪些項目**——我要能判斷覆蓋率。

另外兩句視情況加:「**缺規格 → 回報,不腦補**」、「交付時附詮釋點清單」(由 leader 裁決後回寫 spec,版本 +1)。

## 三、review 專用

- **驗證全綠 → 先 commit 鎖 baseline → 才 spawn review**。審半成品等於審一個不存在的東西。
- **用沒參與實作的 fresh agent**。作者的測試只證明「做了的部分對」,證不了「沒漏做」——佈線/I-O 殼類的洞只有外人逐條對 spec 才抓得到。
- **要 mutation 表,不要只要「有沒有問題」**。派工令寫:「提出具體 mutation:改哪一行 → 你預期哪一條測試會紅;**若你認為某個 mutation 不會讓任何測試紅,明確指出**。」——後半句才是有價值的那半。**零覆蓋最常藏在「看起來有測」的地方**:實證某輪兩個 0 紅缺口,一個是斷言用的輸入剛好在提前返回就 return 了、**根本沒進要驗的分支**(而註解描述完全正確,只是描述的是別的東西);另一個是**不做單元測試的 class 裡的私有方法**——那等於「該邏輯在任何 mutation 下都不會紅」,把它抽成可測的純函式,成本遠低於它守的東西。
- **告訴 reviewer 去找權威來源,別只給你的轉述**。派工令若只貼「使用者說契約是這樣」,reviewer 只能標「無法驗證」。明講「若 `../<repo>` 在本機,直接讀原始碼核對」——實證某輪兩位 reviewer 各自去讀了後端原始碼,一位因此**撤回**原本要報的「未經驗證的斷言」,另一位反過來證實了我方註解對後端計數方式的假設。**轉述的規格是二手的,而一手的通常就在隔壁資料夾。**
- **review 期間 baseline 凍結,作者 agent 必停**。有寫入權的閒置 agent 是審查污染源;leader 自己也不要動檔案,否則後續報告是對著失效的 baseline 寫的。
  > **非動不可時的解法:把範圍釘在 commit hash 上,然後往上疊新 commit、絕不改寫被釘的那幾顆。** 派工令寫「只審 `<hash>`」而不是「審目前的工作區」,reviewer 讀的東西就不會被你後來的動作改掉,報告仍然有效。踩過的反面:`git commit --amend` 或 rebase 會讓被指派的 hash 消失,reviewer 手上的行號與結論一起作廢。(實證:某輪我在 review 進行中加了診斷 log,reviewer 主動回報「我開審時 HEAD=X、現在是 Y」,並自行核對確認不影響結論——**它做得到是因為範圍釘的是 hash**。)
- **上一輪修正過的地方,下一輪要重審**。「那塊上次審過了」≠「那塊已經正確」——上一輪的修正是**新寫的、沒有任何人審過的程式碼**,而且通常落在最微妙的位置(併發 guard、生命週期、錯誤路徑),還是在剛被指出問題的壓力下趕出來的。估「這個維度變動了多少」時**要把上一輪的 fix commit 算進去**,別因為「上次審過」就降低它的優先度。
  > 實證:某輪四視角 review 修完狀態層後,下一輪的狀態視角被判定「最薄、大概無發現」,結果回報 3 個 P1——**沒有一個在該輪的新功能裡**,全是上一輪修正自己的洞(值去重漏了錯誤路徑、generation guard 捕捉到已過期的世代、新加的 timeout 與框架 build 覆寫的交互)。

### agent 數由「視角」決定,不設上限

一個視角要成立的唯一條件:**它能抓到其他視角結構上抓不到的缺陷類別**。硬性壓數量會壓抑覆蓋率、漏掉真問題;該問的是「還有沒有沒被覆蓋的缺陷類別」,不是「幾個夠了」。

| 視角 | 專抓 | 何時需要 |
|---|---|---|
| 資料/狀態層 | 契約解析、狀態機、併發、樂觀更新與重拉的競態、生命週期 | 幾乎總是 |
| UI / 手勢 / 版面 | 視覺 regression、hit test 被吃、key 相撞、小螢幕溢出、i18n 截字 | 改到 widget 才需要 |
| 既有功能 regression | 已上線功能被當**附帶損害**改到 | 抽共用件、改共用元件時必開 |
| spec 對照 | **該做而沒做**、做偏、規格沒寫卻自己發明 | 有 spec 且改動大到「漏做」可信時 |
| 有爭議的技術決定 | 單點深挖某個賭注(依賴未定義行為、繞過機制、效能取捨) | 有那種決定時 |

實例:某輪「既有功能 regression」視角抓到的 P1,邏輯視角看不到——觸發路徑在頁面佈線、不在 ViewModel。反例也存在:某輪 UI 視角 80% 結論是「逐行 diff 零差異」,那就是沒有新類別、白開一個。

要 reviewer 交叉驗證時,把**已確認的發現摘要**寫進後續派工令,問「你的視角有沒有獨立看到/有沒有補充」。

## 四、收到 idle 通知時

**`idle` 只代表它停了,不代表它交了**——兩者外觀完全一樣。

1. 沒收到報告 → **先 SendMessage 去要**,提醒它「純文字對我不可見,請用 SendMessage 重傳」。
2. 報告到手 → **自己讀 code 驗關鍵發現**再採信。衝突訊號時**信 code、不信 teammate 散文報告**(報告會 mis-describe 自己的 code;兩份報告打架時尤其如此)。
3. 驗證完、確認無後續工單 → 才 `shutdown_request`。

**先關再說 = 把已經做完的調研丟掉。** 這個順序錯過一次就知道痛。

至於該不該關:後續**已具體化**才指派保溫;後續存在但未具體化(如等 review 結果)視同無後續 → stop。**絕不留 idle-未指派**(會漂移、自認領亂改)。

**但「交付後留著待追問」是有終點的,別只執行前半。** 使用者常想對 review agent 追問細節,所以剛交付時該留;可是話題一收尾(發現全部修完、或轉去做別的事)就該關。踩過:一輪 review 的四個 agent 說「留著待追問」之後**再也沒回頭檢視**,掛了好幾小時,最後是使用者問「怎麼還這麼多掛著」才清掉。**天然的檢視點就是「我要 spawn 新 agent 的時候」**——那本來就要盤點(見一、),開新一輪 review 時上一輪的通常就該關了,不用另外記得。stop≈免費、真 idle 不燒 token、成本在 re-spawn 重載——stop 是擋 drift,不是省 token。stop 用 `shutdown_request`,口頭「請停工」擋不住 idle 迴圈;**上個 session 遺留、已經沒有對話脈絡可談的,直接 `TaskStop` 指名關掉**。

## 五、規格中途大改

**停掉重派,不要 SendMessage 修訂。** 埋頭實作中的 agent 常不收信(交付物照舊規格做完才發現)。改 spec 檔 + 開新 agent 讀新版,比寄信祈禱可靠。派工時把「顏色/易變層集中單一檔」寫進指令,可把這種返工壓到最小。

**替補必須等原 agent 的 `shutdown_approved` 到手才動工——leader 自己接手也算替補**,同樣要等確認。shutdown 與訊息處理都是非同步的,「idle + 分支沒新 commit」不能證明工單沒被吃(可能正在做、未 commit),貿然進場 = 兩個 writer 撞同一個 worktree。等不及就用 worktree 隔離。

## 六、決策回拋

**只三類回拋使用者**:部署、範圍、花錢。其餘 leader 拍板、事後報。
