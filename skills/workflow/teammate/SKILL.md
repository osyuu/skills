# 背景 agent 房規

**review 的方法論不在這裡**——釘固定點、Standards 與 Spec 兩軸並行、報告不合併不重排、
每軸 400 字,全在 `mattpocock-skills:code-review`,那裡是單一真相。這份管的是那套借來的
方法論**結構上不會有**的東西:它用 in-process 的 sub-agent,而背景 agent 會用
**「看起來成功了的失敗」**騙你——報告沒送到卻顯示 idle、agent 照舊規格做完才發現規格改了、
兩個 writer 撞同一個 worktree。

## 一、開之前

- **先盤點現有的**。名稱衝突會長 `-2`(identity 分裂);有對口就 `SendMessage` 復用,別重開。
  `ListAgents` 回空**不代表沒有**,`TaskList` 列的是任務不是 agent;要確認某個名字還在不在,
  `SendMessage` 指名送一則,送得到就活著。**上個 session 留下的 teammate 對新 session 是
  隱形的**,所以盤點的最後一步是問使用者看 `/tasks`——不問就會在它們還掛著的時候又開一輪。
  停掉用 `TaskStop`(吃名字,跨 session 也吃)。
- **按任務性質分 model**:async/併發/生命週期/測試 harness → 強模型;規格鎖死的機械 UI → 輕模型。
  **review 也要分,判準是「這個視角要的是執行還是判斷」**:跑指令、比對輸出、驗冪等、掃 grep
  → 便宜模型就夠,那是打字不是想事情;「這條規則會不會被鑽 / 這個門檻站不站得住 / 該不該做」
  → 才值得最強或**最不同**的那個。**把貴模型用在執行上,買到的是同樣的輸出加上帳單。**
- **可重複的執行本來就不該是 agent**。手做一次是為了把案例寫成測試,不是為了每次重做——
  同一批案例第二次還要派人跑,就是該寫 `tests/` 了。
- **大改跨檔用 worktree 隔離**,主 tree 保持穩定給別的並行工作(QA/截圖)。

## 二、派工令必備七條

1. **唯讀還是可寫**,講死。review/調研一律唯讀:「不要編輯、新增、刪除任何檔案,也不要 commit」。
2. **回報方式**:
   > 你的純文字輸出**對我不可見**,必須用 **SendMessage 工具**傳給 `main`(或 `team-lead`)。
   > 做完就傳,**不要進 idle 等我來要**。

   不寫這條,agent 會安靜跑完然後 idle,成果鎖在它自己的 transcript 裡。**這是最常見也最貴的
   失敗**,而 in-process 的 sub-agent 沒有這個問題——所以借來的 review skill 不會提醒你。
3. **範圍**:commit 區間(`git log --oneline <base>..HEAD` 貼上)+ 背景文件路徑 +「完整讀完」。
4. **必查清單**:具體到「這個函式在這四種情境下各會怎樣」,不要只給主題。
   **把自己最不確定的那一點明著寫進去要它攻**——brief 決定 reviewer 看得到什麼,略過那一點
   等於把自己的假設洗過第二個模型再拿回來。實證:某輪唯一的 P0 就是這句話換回來的,
   而當時完全可以選擇不寫。
5. **排除既有雜訊**:「`test/xxx` 的 N 個失敗是既有的、與本次無關,不要當成你的發現」。
   不寫的話報告會被既有紅燈灌水。
6. **回報格式**:
   > 格式:「檔案:行號 / 嚴重度(P0阻斷|P1應修|P2建議) / 具體失效情境(什麼操作序列 →
   > 什麼錯誤結果)/ 建議修法」。**每軸 400 字以內**,最重要的放最後,超過就分批:
   > 「每批 150 行以內,發完等我回『下一批』」。
   > 不要提無實質影響的風格意見,也不要為了湊數硬報。不確定就明說不確定,並講清楚**需要什麼
   > 證據**才能確認。**「這裡有問題,但不值得修」是完整的結論**,不是放水。沒問題就說
   > 「審完、無發現」,並列出你**實際驗證了哪些項目**——我要能判斷覆蓋率。

   長度上限不寫的話**單則通知裝不下就會被截斷**,而截斷方向不固定(實測有從結尾掉的,
   也有從開頭掉的)。踩過:一輪 review 截斷六次,吃掉的比 review 本身多。
7. **寫成「證明我錯」,不是「幫我看看」**:
   > 你的任務是**證明這份改動是錯的**:構造能通過我的檢查卻會壞掉的反例,逐一推翻我的每個
   > 判斷。攻不破的說「這項我攻不破」,沉默不是背書——但不要為了交代而逐條複述,列出你
   > 實際驗過哪些就夠了。

   **低要求的 prompt 拿不到反例。**「幫我看看」要的是意見,「證明我錯」要的是反例——
   同一個模型,兩種產出。

   > **何時適用**:**預設適用**。**交付的第一句話要包含「這份有/沒有外審」**——有外審也要
   > 正面說。豁免只有一種形狀:明說沒有然後交付;**默不作聲不算豁免**——只列事實、不下結論地
   > 交出去,讀的人會自己補上那句判決,而那正是最省事的規避方式。只要要講「這是對的 / 修好了 /
   > 可以合了」,**行數與範圍無關**(4 行 regex 出過 2 個 P0)。**這句管的是「要不要找人看」,
   > 不管「要看幾輪」**——後者見 `dev-loop`〈要不要再跑一次〉。
   > 這條**不是**把該自己抓的缺陷推給 review:自己該跑的檢查照跑,對抗式 review
   > **疊在那之上、不代替它**。

另外兩句視情況加:「**缺規格 → 回報,不腦補**」、「交付時附詮釋點清單」(由 leader 裁決後
回寫 spec,版本 +1)。

## 三、reviewer 會執行東西時才適用的

`mattpocock-skills:code-review` 假設 reviewer 只讀 diff。**只要你的 reviewer 會跑東西
(跑測試、注入故障、開探針),下面這幾條才開始適用**;純讀 diff 的 review 全部跳過。

- **驗證全綠 → 先鎖 baseline → 才 spawn**。審半成品等於審一個不存在的東西。commit 是鎖
  baseline 最好的形狀,但不是唯一的:沒有 commit 授權時釘一份 `git diff` 或
  `git stash create` 的產物,派工令附路徑。**工作區當 baseline 才是壞的那種**——你後續
  每一次存檔都在讓報告失效。
- **釘 hash 是預設,不是例外——而且你不必跟著閒置。** 派工令寫「只審 `<hash>`」而不是
  「審目前的工作區」,你就可以繼續往上疊新 commit(**絕不改寫被釘的那幾顆**:`--amend` 或
  rebase 會讓被指派的 hash 消失,reviewer 手上的行號與結論一起作廢)。**review 與實作該
  並行,不是排隊**——它們互相抓不到對方:review 抓跨章節的不一致,執行抓數值與定義域。
  踩過:一輪 review 期間作者全程閒置約 40 分鐘,而其中一個 P0(浮點平手)把規格逐字實作
  出來跑一次就是紅的。
  有寫入權的**閒置未指派** agent 仍然是污染源(它會自認領亂改),那是要 stop 它的理由,
  不是「所有人都不准動」的理由。
- **會執行的 reviewer 各給一個 worktree,派工當下就開好**(`git worktree add --detach
  <path> <hash>`)。「作者停了」不等於隔離完成——**reviewer 之間也會互相污染,而這一種
  沒有任何跡象**:實證兩位共用一棵樹,一位建的暫時探針讓另一位跑出 216/18(baseline 是
  210/17);更糟的是同時注入同一個檔時,任一方 `git checkout` 還原就清掉對方的注入,
  **兩邊看到的紅綠全部作廢而輸出跟正常完全一樣**。已經發生的話,搬家之後**重跑污染期間的
  每一條注入**,報告裡把「污染期做的」與「重做過的」分開標。**綠的宣稱比紅的更需要乾淨的樹。**
- **reviewer 不得互相引用**——兩份互相引用的報告只等於一份。要交叉驗證是 leader 的事:
  把**已確認的發現摘要**寫進後續派工令,問「你的視角有沒有獨立看到」。
- **告訴 reviewer 去找權威來源,別只給你的轉述**。只貼「使用者說契約是這樣」,reviewer 只能
  標「無法驗證」;明講「若 `../<repo>` 在本機,直接讀原始碼核對」。**轉述的規格是二手的,
  而一手的通常就在隔壁資料夾。**
- **要加第三個視角,唯一的條件是:它能抓到那兩軸結構上抓不到的缺陷類別。** 說得出那個類別
  才加。實證兩邊都有:某輪「既有功能 regression」視角抓到的 P1,邏輯視角看不到(觸發路徑在
  頁面佈線、不在 ViewModel);而某輪 UI 視角 80% 的結論是「逐行 diff 零差異」,那就是白開
  一個。**別自己發明守備範圍**——派過「實作正確性 / 測試品質」,兩位讀同一批 code、獨立撞到
  同一個 P0,那是重複不是覆蓋。
- **上一輪修正過的地方,如果還要再跑一輪,那一輪要涵蓋它**(要不要再跑見 `dev-loop`
  〈要不要再跑一次〉——**「有修正」本身不是理由**)。實證:某輪修完狀態層後,下一輪的狀態
  視角被判定「最薄、大概無發現」,結果回報 3 個 P1,**沒有一個在該輪的新功能裡**,
  全是上一輪修正自己的洞。

## 四、收到 idle 通知時

**`idle` 只代表它停了,不代表它交了**——兩者外觀完全一樣。

1. 沒收到報告 → **先 SendMessage 去要**,提醒它「純文字對我不可見,請用 SendMessage 重傳」。
2. 報告到手 → **自己讀 code 驗過每一條 P0/P1** 再採信;P2 掃過即可。(第 6 條要的嚴重度標籤
   就是為了讓這一步有邊界——「驗關鍵發現」沒有邊界,而沒有邊界的驗證會停在第一條看起來合理
   的地方。)衝突訊號時**信 code、不信散文報告**——報告會 mis-describe 自己的 code,
   兩份報告打架時尤其如此。
3. 驗證完、確認無後續工單 → 才 `shutdown_request`。**先關再說 = 把已經做完的調研丟掉。**

該不該關:後續**已具體化**才指派保溫;後續存在但未具體化(如等 review 結果)視同無後續
→ stop。**絕不留 idle-未指派**(會漂移、自認領亂改)。「交付後留著待追問」是有終點的,
別只執行前半——話題一收尾(發現全部修完、或轉去做別的事)就該關。踩過:一輪 review 的四個
agent 說「留著待追問」之後再也沒回頭檢視,掛了好幾小時。**天然的檢視點是「我要 spawn 新
agent 的時候」**——那本來就要盤點(見一、)。stop≈免費、真 idle 不燒 token,成本在 re-spawn
重載——**stop 是擋 drift,不是省 token**。口頭「請停工」擋不住 idle 迴圈,用
`shutdown_request`;上個 session 遺留、已經沒有對話脈絡可談的,直接 `TaskStop` 指名關掉。

**review 收完之後棒子交回哪**:findings 逐條有結論(修掉、或標「接受不修＋理由」)就回
`dev-loop` 核〈完成的定義〉那**兩條**(驗收標準逐條有結論、翻案已回寫 spec)。
**review 不在那兩條裡**——它是第 4 棒的動作,不是完成條件。

## 五、規格中途大改

**停掉重派,不要 SendMessage 修訂。** 埋頭實作中的 agent 常不收信(交付物照舊規格做完才
發現)。改 spec 檔 + 開新 agent 讀新版,比寄信祈禱可靠。派工時把「顏色/易變層集中單一檔」
寫進指令,可把這種返工壓到最小。

**替補必須等原 agent 的 `shutdown_approved` 到手才動工——leader 自己接手也算替補**,
同樣要等確認。shutdown 與訊息處理都是非同步的,「idle + 分支沒新 commit」不能證明工單沒被吃
(可能正在做、未 commit),貿然進場 = 兩個 writer 撞同一個 worktree。等不及就用 worktree 隔離。

## 六、決策回拋

**只四類回拋使用者**:部署、範圍、花錢、**連續的 review 輪次**。其餘 leader 拍板、事後報。

第四類是第三類的一種,單獨列出來是因為它不長得像花錢:**它花的是使用者的時鐘,而那個預算
只有他看得到**。第二輪起,先說「我要再跑一輪、為什麼」再跑。踩過:五輪連跑約 40 分鐘,
使用者離開又回來才發現還在審。
