# handoff — 交接:只寫 repo 查不到的東西

## 為什麼需要一套流程

**交接發生在你最不可靠的時刻**:context 最稀、剛壓縮過、剛做完幾百個回合。而這時要做的偏偏是
「回想哪些東西重要」——用記憶去挑記憶。

這跟 `DECISIONS.md` 那條「翻案當下就記,不要留到交付前憑記憶重建」是同一個病。差別在於決策
可以當下就寫,而交接**只能在尾聲做**,所以更需要一份不靠當下判斷力的清單。

**開新 session 優於 compact——但前提是交接寫好了。** 兩者丟掉的東西不同:compact 保留對話摘要
但**skill 版本凍結在當初抓的那份**（開很久的 session 會照著舊規則工作）;新 session 重載
skill、CLAUDE.md、記憶索引,但**沒寫下來的一律失憶**。交接沒做好時,compact 反而較安全。

## 流程

**1. 先跑機械盤點**（這部分不該靠記憶）:

```
sh <skill-dir>/scripts/state.sh
```

**它機械列得出來的只有三樣**:未 commit、未 push、殘留的 worktree。其餘三樣(還活著的
agent／注入過的故障還原並重建了沒／哪些是宣稱完成但沒驗過)它只印提示——那些它查不到,
所以它不假裝查過。**別把提示讀成「已盤點」。**

尤其**回報時別把它們寫進「機械盤點」那一段**——憑記憶答出來的東西一旦排進機械盤點的表格,
讀的人就分不出它是查來的還是想出來的,而那正是這支腳本存在的理由。(實地踩過:一個 session
跑完 state.sh,把「這個 session 沒開過背景 agent」列進盤點結果——腳本從沒檢查過那件事,
答案剛好是對的。)

**agent 那項要另外真的點名**:`jobs` 只看得到本 shell,上個 session 遺留的對這個 session
是隱形的。點名的辦法見 `teammate` 的〈一、開之前〉,最後一步是問使用者。**踩過:收尾時憑
印象數關了幾個 agent,漏掉一個閒置到使用者手動殺掉**——閒置的 agent 看起來跟關掉的一模一樣。

**2. 再挑要寫進記憶的東西。** 唯一的判準:

> **只寫 repo 查不到的東西。**

| 寫 | 不寫（repo 已經有了） |
|---|---|
| 還沒決定、等使用者拍板的事 | 改了哪些檔（`git log`） |
| **否決過的路與理由**（否則下次會重走一遍） | 為什麼這樣實作（design doc／註解） |
| 量出來的數字與它的取樣（「26 筆裡 17 筆 ≥1.5 倍」） | 目前的架構（code 本身） |
| **哪些是宣稱完成但沒驗過的** | 已經寫進 CLAUDE.md 的約束 |
| 使用者講過的判準與偏好 | commit 訊息裡已經有的 |

**寫了 repo 已有的東西，等於製造第二份會腐爛的真相**——而它腐爛時沒有任何機制會發現。

**3. 分類與格式**照記憶檔既有慣例（`user` / `feedback` / `project` / `reference`），
一個檔一件事,並在 `MEMORY.md` 補一行指標。**先找有沒有既有檔涵蓋了**——更新它，不要開新的。

## 容易漏的四類（每次逐條問一次）

1. **沒驗的東西。** 「實機未驗」「UI 沒看過」「這條規則的真陽性還沒確認」——不寫的話，
   下一個 session 會當成驗過了，然後在它上面繼續蓋。
2. **待決的問題。** 明確寫出「在等使用者回答什麼」，而不是「下一步是 X」。
3. **否決過的路。** 只寫結論的話，下一個 session 會把同一條路再走一次；理由比結論值錢。
4. **這一輪犯的錯與成因。** 尤其是「機制擋不住、靠人抓到」的那種——它會再犯。

## 品質自檢

- 每一筆都通得過「repo 真的查不到嗎」？查得到的刪掉。
- 「待決」寫的是**問題**還是**下一步**？只寫下一步的話，下個 session 會直接做，跳過該問的。
- 沒驗的東西列出來了嗎？（這是最常漏、後果最貴的一類。）
- 機械盤點跑了嗎，還是憑印象講「都乾淨了」？
