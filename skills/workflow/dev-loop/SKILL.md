# dev-loop — 從需求到交付的接力

每一棒的做法在各自的 skill 裡,那裡才是單一真相;這支只管**交棒**與**每一棒的完成條件**。

## 四棒

| 棒次 | 交給誰 | 這一棒完成的條件 |
|---|---|---|
| 1 收斂需求 | `design-doc` | 設計書有驗收標準,且每條**可判定**(能回答「失敗長什麼樣」) |
| 2 定順序 | 見〈第 2 棒〉 | 動哪些檔、什麼順序、怎麼驗,**三件都寫下來了** |
| 3 實作 | 見〈執行器降檔〉;要寫測試前先定 seam(`mattpocock-skills:tdd`——它要求 **confirm them with the user**,掛在動作上比掛在階段上難漏) | 該專案自己那套檢查全綠,**且最後一次改完之後又跑過一次** |
| 4 回環驗收 | `mattpocock-skills:code-review` + `design-doc` Step 5 | **跑過一次,findings 逐條有結論**(見〈Review 是一個 stage〉) |

**第 4 棒是這支 skill 存在的主要理由。** `design-doc` 的 Step 5(回環驗收 + 回寫)論證過
「過期的 spec 比沒有 spec 更危險」,但它的觸發詞全在**開發前**——實作完成後沒有任何句子
把它拉回來。這裡就是那句話。

## 第 2 棒:定順序

三個答案寫下來:**動哪些檔**與順序(有依賴的串行,無依賴的才並行)、**怎麼驗**每一步、
**夾不夾 codegen / migration** 這類 barrier(它決定能不能並行)。寫得出來就往下走;
寫不出來表示第 1 棒還沒收斂,回去補設計書。

## 執行器降檔

**預設往低檔走**,plan 的形狀決定執行器,不是反過來:

- plan 是**一條垂直切片**(同一條功能貫穿它會經過的每一層,共享型別與狀態——可能是資料層
  到畫面,也可能是 parser 到輸出、或一支 CLI 從參數解析到副作用)→ **主線直改**,或想保持
  主線乾淨就開**單一 sub-agent**。多數 feature 屬此。
- 攤得開成 **2 條以上互不依賴、各動各的檔**的並行流,且每塊夠大攤平 worktree 開銷 →
  才升 **agent team + worktree**(房規見 `teammate`)。開一個 worktree 要跑哪幾步是
  **per-repo 的**,那筆開銷記在 `repo-onboard` 寫的 profile 裡,別用一個預設數字代替它。

「寫了設計書」不構成升 team 的理由——單一 feature 本質環環相扣、反並行,硬拆會換來
context 碎裂 + 整合漂移,協調開銷大於並行收益。

## 完成的定義

**兩條**:

1. **驗收標準逐條有結論**——通過 / 不通過 / 跑不了＋為什麼。**空白等於沒跑**,不是預設通過。
2. **翻案與新增決策已回寫設計書**(版本 +1)。翻案的當下就記,不要留到交付前憑記憶重建——
   那一刻 context 最稀,也最不可靠。

**沒有設計書時**(多數 bug 票與小改動都是,`design-doc` 自己也寫「解法顯而易見就別寫」):
第 1 條讀作「**票/需求裡的驗收條件逐條有結論**」,一條都找不到就明說「無可驗收條目」
——那本身是個發現;第 2 條讀作「翻案寫進 commit message」。**明說走的是哪一種**。

## Review 是一個 stage,不是一道閘門

**第 4 棒要跑,而它的產出是一份報告,不是一個必須清空的待辦。** P0/P1 要嘛處理掉、
要嘛明說「接受不修＋理由」,兩者都算處理完,然後交付。

**怎麼跑見 `mattpocock-skills:code-review`**:釘住一個固定點、Standards 與 Spec 兩軸並行、
**報告不合併也不重排**、每軸 400 字。那裡是單一真相,這裡不複製一份。背景 agent 的操作面
(回報方式、baseline、idle)見 `teammate`。

**不要跑 `/setup-matt-pocock-skills`。** 它會裝進一套 issue tracker 當 spec 權威,而這類
repo 的權威通常已經在設計書 / `DECISIONS.md` / `testvectors/` 裡——**第二套權威就是最貴的
那種 drift**。沒有 tracker 時走 `code-review` 第 2 步的第 2/3 分支:**把設計書的那一節
(或票的路徑)當 spec source,並在派工令裡明說本 repo 無 tracker**。

**寫成完成條件的話它必然不會停**:「P0/P1 都處理掉才算完成」＋「修正是新寫的、沒人審過
的 code」＝ 每個修正都生出下一輪,一個沒有不動點的遞迴。踩過:一節畫面規格連跑五輪、
約 40 分鐘、作者全程閒置。

### 要不要再跑一次

修正是新寫的、沒人看過的東西,所以再跑一次經常是對的——但**「有修正」本身不是理由**。
派之前寫兩行,寫不出來就是還沒想清楚:

- **這一輪要抓哪一類缺陷,有沒有比 review 更快的驗法?**
  - **跑得起來就跑**——純函式、算式、有唯一預期值的東西。**說得出檔名或函式名的話,
    那一輪 review 多半在等一個執行五分鐘就有的答案。**
  - **守門、測試假件、harness 用注入**(故意造一個該被抓到的違規,看它會不會紅),不是外審。
    代價算的是**你要寫的那個東西**壞掉的代價,不是它守的東西壞掉的代價——**這一格最容易被
    繞過**,繞法是指著被守的東西說「這很重要」,然後對守門本身跑產品級紀律。
  - **跨章節、跨檔案的一致性沒有更快的驗法**,那才輪到 review。
  - **全綠不等於有蓋到**:對新寫的測試提一份 mutation 表——「改哪一行 → 你預期哪一條測試
    會紅;**若某個 mutation 不會讓任何測試紅,明確指出**」。後半句才是有價值的那半。
- **如果這一輪回報「無發現」,我會不會就交付?** 答「會」才值得跑。答「不會」表示我在等它
  替我做決定,而攻擊式的 review 結構上給不出「夠了」。

**第二輪起,先告訴使用者你要再跑一輪、為什麼,再跑**(`teammate` 六的第四類)。
花的是使用者的時鐘,而那個預算只有他看得到。

## 交付時要說的

交付的第一句話要包含「這份**有/沒有**外審」。有外審也要正面說;豁免只有一種形狀:
**明說沒有然後交付**,默不作聲不算。完整規則在 `teammate`〈二〉第 7 條。

**守著這條的主要是紀律。** 機械那側是 `claim-check` 的〈正確性宣稱〉(最後一次改 code
之後一個 agent 都沒派過就開火),但**它只認結論詞**,所以覆蓋邊界是:

- **不下結論的交付它一個字都看不到**——包含依上面那條寫成的第一句話本身。
- 詞表中英各一半,其他語言沒補進 `claim-check.conf`(`CLAIM_*_CLAIM_RE`)就是
  **一次都不開火**——跟很誠實長得一樣。
- `SendMessage` 也算「派過人」,跟隊友講一句話就能讓它閉嘴。

## 交付前的整理

**loop 中的 commit 是 checkpoint,不是交付單位。** 一輪下來多半有好幾顆是「修上一顆的
問題」,那個歷史記錄的是迭代過程,不是變更的邏輯結構。push 之前整理一次:squash 成邏輯
單元、重寫 commit message。**只准做不改 tree 的事**——判準是機械的,整理完
`git diff <整理前的 hash> HEAD` **必須是空的**。

**時機只有一個:review 收完之後。** rebase 會改寫 hash,而 review 的範圍釘在 hash 上,
先整理會讓還沒交付的報告連行號一起作廢。這也是為什麼 review 期間要疊新 commit 而不是 amend。

**清 pre-commit 的累積 warn 排在 review 派出去之前**(warn 會被滾過去,今天不清就永遠不清)。
它改的是 code,而 review 之後改 code 就是「交出去的那份沒人看過」——交付時要說得出來。

## 這個 repo 還沒配置過守門的話

先跑 `repo-onboard`(探測技術棧、配 harness、寫 per-repo 配置、注入故障驗證每一道會開火)。
沒有守門的 repo,第 3 棒的「全綠」只證明得了你記得跑的那幾樣。
