# dev-loop — 從需求到交付的接力

每一棒的做法在各自的 skill 裡,那裡才是單一真相;這支只管**交棒**與**每一棒的完成條件**。

## 四棒

| 棒次 | 交給誰 | 這一棒完成的條件 |
|---|---|---|
| 1 收斂需求 | `design-doc` | 設計書有驗收標準,且每條**可判定**(能回答「失敗長什麼樣」) |
| 2 定順序 | 見下方〈第 2 棒〉 | 動哪些檔、什麼順序、怎麼驗,**三件都寫下來了**(回覆或 plan 檔裡看得到那三行) |
| 3 實作 | 見下方〈執行器降檔〉 | 該專案自己那套檢查全綠,**且最後一次改完之後又跑過一次** |
| 4 回環驗收 | `teammate`〈寫成「證明我錯」〉+ `design-doc` Step 5 | 見下方〈完成的定義〉 |

**第 4 棒是這支 skill 存在的主要理由。** `design-doc` 的 Step 5(回環驗收 + 回寫)寫了整整一節
論證「過期的 spec 比沒有 spec 更危險」,但它的 description 觸發詞全在**開發前**——實作完成後
沒有任何句子把它拉回來。這裡就是那句話。

## 第 2 棒:定順序

plan 不需要另一支 skill,它要的是三個答案寫下來:

- **動哪些檔**、什麼順序(有依賴的串行,無依賴的才並行)
- **怎麼驗**——每一步的驗證方式,不是「寫完再說」
- **夾不夾 codegen / migration** 這類 barrier(它決定能不能並行)

寫得出來就往下走;寫不出來表示第 1 棒還沒收斂,回去補設計書。

## 執行器降檔

**預設往低檔走**,plan 的形狀決定執行器,不是反過來:

- plan 是**一條垂直切片**(同一條功能貫穿它會經過的每一層,共享型別與狀態——可能是資料層
  到畫面,也可能是 parser 到輸出、或一支 CLI 從參數解析到副作用)→ **主線直改**,
  或想保持主線乾淨就開**單一 sub-agent**。多數 feature 屬此。
- plan 攤開後裂得成 **2 條以上互不依賴、各動各的檔**的並行流,且每塊夠大攤平 worktree 開銷
  → 才升 **agent team + worktree**(房規見 `teammate`)。開一個 worktree 要跑哪幾步是
  **per-repo 的**(有的近乎零成本,有的要重跑依賴、codegen、憑證拷貝才跑得起來),那筆開銷
  記在 `repo-onboard` 寫的 profile 裡,別用一個預設數字代替它。

「寫了設計書」不構成升 team 的理由——清楚的 plan 通常反而印證這是一條連貫切片。
單一 feature 本質環環相扣、反並行,硬拆會換來 context 碎裂 + 整合漂移,協調開銷大於並行收益。

## 完成的定義

**三條全滿足才叫「完成」。** 只滿足第 1、3 條時仍然可以交付,但那時說的是
「**改完了,這份沒有外審**」——**「完成」這個詞留給三條都滿足的情況**。
缺哪條就明說缺哪條;空著等於替讀的人下了那個判決。

1. **驗收標準逐條有結論**——通過 / 不通過 / 跑不了＋為什麼。**空白等於沒跑**,不是預設通過。
2. **有外審回報**(審的人沒參與實作),其中的 P0/P1 已處理,或明確標為「接受不修 ＋ 理由」。
   派工令怎麼寫、為什麼要對抗式、baseline 怎麼凍結,全在 `teammate`。
3. **翻案與新增決策已回寫設計書**(版本 +1)。翻案的當下就記,不要留到交付前憑記憶重建——
   那一刻 context 最稀,也最不可靠。

**沒有設計書時**(多數 bug 票與小改動都是,`design-doc` 自己也寫「解法顯而易見就別寫」):
第 1 條讀作「**票/需求裡的驗收條件逐條有結論**」,一條都找不到就明說「無可驗收條目」
——那本身是個發現;第 3 條讀作「翻案寫進 commit message」。**明說走的是哪一種**。
第 2 條不因此鬆動。

第 2 條的理由只有一句:**作者驗證不了自己沒想到的東西**。改動大小不影響這個前提。

## 交付時要說的

交付的第一句話要包含「這份**有/沒有**外審」——完整規則(含豁免只有這一種形狀、默不作聲不算)在 `teammate`〈二〉第 7 條的〈何時適用〉,那裡是單一真相。

機械那一側是 `claim-check` 的〈正確性宣稱〉規則:下了正確性結論、而最後一次改 code 之後
一個 agent 都沒派過,就開火。**它認的是結論詞**(十來個固定字串),所以覆蓋邊界是:

- **不下結論的交付它一個字都看不到**——包含依上面那條寫成的第一句話本身。
- 詞表只認中文,英文只有 `LGTM`。
- `SendMessage` 也算「派過人」,跟隊友講一句話就能讓它閉嘴。

也就是說第 2 條的執行力主要仍在紀律那一側;機械那側接得住的是最裸的一種。

## 交付前的整理

**loop 中的 commit 是 checkpoint,不是交付單位。** 一輪下來多半有好幾顆是「修上一顆的問題」,
那個歷史記錄的是迭代過程,不是變更的邏輯結構——跟 commit message 不寫會話過程是同一條。

所以在 push 之前整理一次:squash 成邏輯單元、把累積的 pre-commit warn 清掉
(warn 會被滾過去,今天不清就永遠不清)。

**時機只有一個:所有 review 收完之後。** rebase 會改寫 hash,而 review 的範圍就釘在 hash 上——
先整理會讓還沒交付的報告連行號一起作廢。這也是為什麼 review 期間要疊新 commit 而不是 amend。

## 這個 repo 還沒配置過守門的話

先跑 `repo-onboard`(探測技術棧、配 harness、寫 per-repo 配置、注入故障驗證每一道會開火)。
沒有守門的 repo,上面第 3 棒的「全綠」只證明得了你記得跑的那幾樣。
